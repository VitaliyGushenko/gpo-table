# Как устроена агентная конфигурация is_nsi в OpenCode — схемы

Локальный справочник для разработчика: что существует, что когда включается, как течёт типовая задача.
Правила живут в скилах — здесь только картинки. Символы: `→` «приводит к», `[скилл]` скилл, `/команда`
slash-команда, `(агент)` субагент.

Канон правил — `.zcode/skills/` (его правит zcode и человек). Всё, что в `.opencode/`, — рабочие копии
для OpenCode; см. §9 про то, что синкается автоматически, а что нет.

---

## 1. Из чего состоит конфигурация

```
.opencode/
├── skills/            12 СКИЛЛОВ — ПРАВИЛА (зеркало .zcode/skills, синкается плагином)
│   ├── dev/           ├── хаб: загружается первым для любой задачи
│   │   └── references/│   ├── components.md   образцы dumb/state/токенов
│   │                 │   ├── refactoring.md   плейбук перевода легаси-страницы
│   │                 │   └── graphql.md       конвенции GraphQL + кодеген
│   ├── architecture/  ├── проектирование до кода (стек-агностично)
│   ├── naming/        ├── имена
│   ├── comments/      ├── докблоки
│   ├── critique/      ├── самокритика ДО показа решения
│   ├── review/        ├── ревью чужого/своего diff
│   ├── commit/        ├── формат коммитов, ветки, MR
│   ├── testing/       ├── jasmine-спеки: что и как тестировать
│   ├── debug/         ├── порядок поиска причины бага
│   ├── performance/   ├── виртуализация, пейджинг, воркеры, мемоизация
│   ├── security/      ├── innerHTML/санитизация, токены, Sentry
│   └── ui-texts/      └── тексты UI, даты/числа проектными pipe
│
├── agents/            2 СУБАГЕНТА — ИСПОЛНИТЕЛИ (mode: subagent + permissions)
│   ├── frontend-reviewer.md   read-only ревью diff «глазами со стороны»
│   └── frontend-tester.md     пишет/проверяет *.spec.ts, продуктовый код не трогает
│
├── commands/          5 КОМАНД — ЯВНЫЙ ВЫЗОВ (/check, /review, /commit, /spec, /sync-skills)
│
└── plugins/
    └── is-nsi.ts      АВТОМАТИКА: prettier после правок + синка скилов (см. §6)

AGENTS.md (корень)     точка входа: карта репо + маршрутизация. Загружается в контекст КАЖДОЙ сессии.
.zcode/skills/         КАНОН правил; .opencode/skills — его зеркало для OpenCode
```

## 2. Как скилл «включается» — progressive disclosure

Скилл не работает как скрипт. Это текст с правилами, который подмешивается в контекст модели, когда он уместен:

```
ВСЕГДА в контексте:  name + description каждого скила (метаданные, ~12 строк)
                             │
   фраза пользователя ───────┤ совпала с description («проверь код», «тормозит»…)
                             ▼
ЗАГРУЖАЕТСЯ ПОЛНОСТЬЮ: тело SKILL.md (~30–110 строк правил), инструмент `skill`
                             │
   в теле есть указание ─────┤ «прочитай references/components.md перед…»
                             ▼
ПО ТРЕБОВАНИЮ:       references/*.md (образцы, детали) — только если нужны
```

Следствие: `description` в frontmatter — это и есть «кнопка включения». Плохое описание = скил молчит.
ID скила в OpenCode — имя каталога (`dev`, `review`, …), `name` во frontmatter — только подпись.

## 3. Жизненный цикл типовой задачи разработки

```
 Пользователь: «Добавь колонку „Ответственный“ в таблицу планов»
        │
        ▼
 (1) [dev] ───────── первый: стек, целевая архитектура, процесс
        │
        ├── (2) [architecture] ─── требование → границы → контракт → план (нетривиальное — показать)
        │
        ├── (3) код ──┬── [naming]     имена новых сущностей
        │             ├── [comments]   докблоки
        │             ├── [ui-texts]   заголовок колонки, формат значений
        │             └── references/  components.md (образцы), graphql.md (если запросы)
        │
        ├── (4) [critique] ─────── прогон решения ДО показа (гонки, пусто, права, регрессии)
        │
        ├── (5) [review] ───────── self-review своего diff перед завершением
        │
        └── (6) [commit] ───────── сразу после задачи: коммит + push (если не отложено)
```

Шаги — не церемония: (1)–(2) до кода, (3) во время, (4)–(5) до показа, (6) сразу после задачи. Мелкая правка может
пройти весь путь «свернуто» — но каждый пункт проверяется.

## 4. Сценарии: фраза → что происходит

| Сценарий / фраза | Главный поток | Подключается по ходу |
| --- | --- | --- |
| **Новая страница/фича** «нужно добавить…» | `[dev]` → `[architecture]` → код → `[critique]` → `[review]` | `references/components.md`, `[naming]`, `[ui-texts]` |
| **Правка поведения** «поменяй…» | `[dev]` → классификация изменения (`[architecture]` §4) → код → `[critique]` | `[review]`, `[ui-texts]` |
| **Баг** «не работает / показывает не то» | `[dev]` → `[debug]`: воспроизвести → причина (типовые: кодоген, OnPush, кэш Apollo) → минимальный фикс | `[testing]` (регрессионный спек: красный → фикс → зелёный) |
| **Рефакторинг легаси-страницы** | `[dev]` → `references/refactoring.md`: карта → токен → state-сервисы → dumb → зачистка; шаг = коммит `[refactor]` | `[commit]`, `[review]` |
| **Ревью** «проверь код / PR / ветку» | `[review]`: замысел → diff → потребители → чек-лист → P1–P3 → вердикт | большой diff → `(frontend-reviewer)` вторым независимым проходом |
| **Тесты** «покрой тестами» | `[testing]`: логика, не обвязка; фабрики-литералы; typecheck | или делегировать `(frontend-tester)` |
| **Коммит** «закоммити / запушь» | `[commit]`: номер из ветки → тег → текст → push | — |
| **Тормозит** «висит / долго грузится» | `[performance]`: сначала измерить → готовый механизм (gpo-lib виртуализация / пейджинг / воркер / memoDictionary) | `[dev]` (куда вписать) |
| **HTML из данных / токены** | `[security]`: innerHTML без bypass, что не идёт в Sentry | `[review]` (на ревью — P1) |
| **Тексты/формат вывода** «как сформулировать» | `[ui-texts]`: паттерны кнопок/модалок/ошибок + таблица pipe | `[naming]` (термины) |

## 5. Субагенты: когда и зачем

Субагент — отдельный запуск модели со СВОИМ контекстом (не видит вашу сессию) и своим кругом прав.
Ценность именно в изоляции: свежий взгляд или параллельная работа.

```
 Главный агент (вся сессия, весь контекст)
        │
        ├── «нужен взгляд со стороны» ──→ (frontend-reviewer)
        │        читает только diff/код + скиллы review/dev
        │        permissions: edit запрещён → физически не может править
        │        ↳ вердикт + P1–P3
        │
        └── «нужны спеки» ─────────────→ (frontend-tester)
                 читает скилл testing + тестируемый код
                 permissions: edit разрешён только **/*.spec.ts
                 ↳ пишет *.spec.ts, гоняет tsc; продуктовый код не трогает
```

Правило большого пальца: главный агент сам делает то, что требует контекста беседы; субагенту отдают то,
что должно быть независимым (ревью) или механическим (спеки). В OpenCode субагент запускается инструментом
`subagent` и работает в дочерней сессии; его `description` видит родительская модель при выборе.

## 6. Автоматика на событиях: плагин вместо хуков

В zcode это хуки `PostToolUse` из `.zcode/config.json`. В OpenCode V2 хуков нет — их роль играет плагин
`.opencode/plugins/is-nsi.ts`, он подхватывается автоматически при старте сервера (и перечитывается при
изменении файла).

```
 Изменение/создание файла инструментом edit | write | patch
        │
        ├── путь внутри src/client/ias/**/*.{ts,html,less}
        │        └──→ prettier --write этого файла (конфиг src/client/ias/.prettierrc)
        │             молча; сбой НИКОГДА не блокирует работу
        │
        └── путь внутри .zcode/skills/**
                 └──→ .zcode/skills → .opencode/skills (точная копия)
                      зеркало OpenCode всегда свежее
```

Ошибки автоматики пишутся в `.opencode/plugin-debug.log` (только сбои, не каждое событие).
Откат prettier-автоматики: переименовать `is-nsi.ts` (например в `is-nsi.ts.off`) — в OpenCode нет
`hooks.enabled: false`.

## 7. Команды: явный запуск сценария

```
/check        самопроверка: tsc → ng lint → prettier --check → verify:codegen → типы спеков
              → сводка таблицей; НЕ исправляет без отдельной просьбы
/review       ревью по скиллу review; аргумент = ветка/коммиты/файлы (пусто = текущий diff);
              крупное → + (frontend-reviewer)
/commit       коммит по скиллу commit; предложит разбивку, если изменения несвязанные
/spec <цель>  спеки по скиллу testing или через (frontend-tester)
/sync-skills  принудительно зеркалировать .opencode/skills (после правок вне сессии)
```

Команда ≠ скил: команда — это сохранённый промпт быстрого вызова. В OpenCode у команды нет поля `skills`
(в отличие от zcode), поэтому в теле команды явно написано «Загрузи скилл `X`» — модель делает это
инструментом `skill`. Доступны только поддерживаемые поля: `description`, `agent`, `model`, `subagent`.

## 8. Кто что знает (память конфигурации)

```
AGENTS.md ──────────── в контексте КАЖДОЙ сессии: карта репо, границы, маршрутизация
description скиллов ── в контексте всегда (это «оглавление» для выбора)
тела скиллов ───────── по триггеру, через инструмент skill
references/ ────────── читаются моделью по пути из тела скила
(субагенты) ────────── НЕ видят сессию; получают задачу в промпте запуска
плагин ─────────────── ничего не знает о контексте; только событие инструмента
```

## 9. Поддержка (кто за кем ухаживает)

```
изменилось правило проекта в задаче
        → обновить соответствующий скил .zcode/skills/… в той же задаче
        → зеркало .opencode/skills обновится само (плагин), проверить: /sync-skills

правка агентов/команд
        → .opencode/agents, .opencode/commands НЕ синкаются автоматически:
          правишь .zcode/agents|commands → обнови и порт в .opencode
          (там другой frontmatter: mode/permissions вместо tools, без skills/argument-hint)

массовая правка скилов
        → сначала бэкап: cp -r .zcode/skills .zcode/skills.backup-<дата>

новый скил / агент / команда
        → формат: frontmatter name + description, описание-триггеры решают всё
        → OpenCode перечитывает скилы на лету; агенты/команды — на старте сессии/сервера
```
