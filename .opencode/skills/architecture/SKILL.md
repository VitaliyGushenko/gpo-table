# Архитектура: новый функционал и изменения существующего

Методика на все случаи: пришло требование → понять → найти место → спроектировать → закодить малыми шагами → проверить. Кодирование — последнее звено, а не первое. Скил не привязан к конкретному стеку; правила конкретного проекта — в `dev`.

## 1. Разбор требования (до кода)

1. **Перескажи требование своими словами** в терминах поведения: кто пользователь, что он видит, что делает, что получает в ответ. Если не получается пересказать — задавай вопросы, а не придумывай.
2. **Ответь на вопросы, которых нет в требовании** — иначе они всплывут в ревью:
   - откуда приходят данные и что происходит при ошибке запроса;
   - что видит пользователь при загрузке, при пустом списке, при отсутствии прав;
   - что происходит при повторном клике (double-submit), при уходе со страницы во время запроса;
   - что после успешного действия (закрыть? остаться? куда перейти? что обновить?).
3. **Найди аналог в проекте.** Почти всё уже делалось: похожая страница, модалка, таблица, запрос. Эталон из проекта важнее красивой выдумки — так новое не расходится со старым.
4. **Определи границы:** что входит в задачу, а что нет. Сверх требование («заодно поправлю») не делается; смежные проблемы — отдельно зафиксировать и сообщить.

## 2. Где живет код (размещение)

1. **Новая сущность — новый файл/компонент/сервис**, а не рост старого. Файл, который разросся, при доработке сначала делят, потом меняют.
2. **Слои и направление зависимостей:** интерфейс (что видит пользователь) → состояние/логика → данные (запросы). Зависимости идут только в одну сторону, от интерфейса к данным. Обратное (запрос из кнопки, разметка из сервиса) — ошибка слоя.
3. **Общее — в общие папки, вариантное — в варианты, локальное — рядом с потребителем.** Если кусок нужен двум страницам — он общий; если одному варианту страницы — он вариантный; если одному экрану — лежит рядом.
4. **Абстракции — не преждевременно.** Выносить общее когда один и тот же (не похожий!) код встретился 2–3 раза и его форма устоялась. Абстракция на один случай хуже копипасты: её придется поддерживать, не имея выгоды.
5. **Дублирование допустимо, пока не стало явным.** Два похожих куска могут разъехаться по требованию; преждевременно слитые — придется разделять.

## 3. Проектирование нового функционала

1. **Сначала контракт, потом реализация.** Опиши границы сущности до кода: входы (данные), выходы (события), имя. Контракт — это интерфейс между тобой и остальным кодом; его потом сложно менять.
2. **Разделение UI и логики:**
   - UI-компонент показывает данные и сообщает о действиях; он не знает, откуда данные и как сохраняются;
   - логика (состояние, действия, запросы) — в отдельном классе/сервисе; она не знает про разметку.
3. **Единственный источник истины.** Каждая порция данных живет в одном месте; всё производное (счётчики, флаги доступности, отфильтрованные списки) вычисляется из него, а не хранится отдельно и не синхронизируется руками.
4. **Состояния по умолчанию проектируются сразу:** загрузка, пусто, ошибка, нет прав, режим просмотра. Не «потом допишем» — именно эти состояния забывают и ловят в проде.
5. **Сайд-эффекты изолированы.** Сохранение, localStorage, кэш, печать — отдельные, явно названные места; они не прячутся внутри «получить данные».
6. **Варианты одного и того же (два типа документа, два режима) — через контракт:** общий код параметризуется интерфейсом/стратегией, вариант подключает реализацию. Не флагами `isX` и ветками `if` в общем коде.
7. **Изменяемое состояние — минимизировать.** Сначала «можно ли вычислить?», потом «можно ли хранить локально?», и только потом «нужно ли общее состояние».

## 4. Изменение существующего

1. **Изучи затронутый код до решения**: изменяемые файлы целиком и всех их потребителей (поиск по классу/селектору/токену/методу). Конкретный порядок для фронта — шаг 1 «Процесса работы» в скилле `dev`; здесь он не повторяется. Типичная ошибка — «сломал соседнюю страницу, которая использовала тот же сервис».
2. **Классифицируй изменение** — от этого зависит всё остальное:
   - **багфикс** — поведение стало правильным, контракты не меняются;
   - **рефакторинг** — поведение не меняется вообще, код движется/чистится;
   - **изменение поведения** — пользователь видит другое; его согласовывают отдельно и не прячут в рефакторинге.
   Смешение типов в одном коммите/диффе — запрещено: сначала рефакторинг, отдельным шагом — изменение поведения.
3. **Минимальный диф.** Не переформатировать, не переименовывать и не «улучшать» то, чего не касается требование. Каждый лишний кусок в диффе — риск и работа ревьюера.
4. **Наружный контракт сохраняется**, если требование явно его не меняет: подписи, имена, форматы хранения. Менять контракт — отдельное осознанное решение с проверкой всех потребителей.
5. **Легаси мешает изменению?** Сначала маленьким рефакторингом выдели нужный кусок наружу (поведение то же), потом меняй выделенное. Не переписывать гиганта целиком «раз уже полез».
6. **Скрытые связи — главный риск:** общий сервис, глобальное состояние, сохранённые в localStorage настройки, подписки на события. Их потребители не видны в изменяемом файле — только поиском.

## 5. Порядок работы (сводно)

Сводный пошаговый процесс (изучить → спроектировать → критика → малые обратимые шаги → самопроверка → self-review) зафиксирован один раз — в «Процессе работы» скилла `dev`. Здесь он не дублируется; этот скил отвечает на вопросы «что и где разместить» и «как классифицировать изменение», а не на «в каком порядке работать».

## 6. Чек-лист «готово»

Новый функционал:
- [ ] контракт ясен и не протекает (UI не лезет в данные, данные не знают про UI);
- [ ] данные текут в одну сторону, источник истины один;
- [ ] обработаны: загрузка, пусто, ошибка, нет прав, повторный клик;
- [ ] ошибки показаны пользователю, индикаторы гаснут в `finally`;
- [ ] имена и комментарии — по скиллам `naming`/`comments`.

Изменение существующего:
- [ ] тип изменения определён (багфикс/рефакторинг/поведение) и не смешан;
- [ ] все потребители проверены, соседние страницы живы;
- [ ] диф минимален, сохранённые настройки/контракты не сломаны;
- [ ] устаревшие комментарии обновлены.

## 7. Антипаттерны

- Кодить до того, как понял требование.
- Рост существующего файла вместо новой сущности.
- Абстракция под один случай; копипаста на третий-четвёртый дубль.
- Флаги и ветки вместо контрактов для вариантов.
- Логика данных в UI-компоненте; запросы из обработчика клика.
- Скрытые сайд-эффекты (запись настроек внутри чтения данных).
- Переписывание работающего кода без требования.
- «Заодно» поправить несвязанное в том же диффе.

## Связь с другими скиллами

| Скилл | Что берёт из него |
| --- | --- |
| `dev` | конкретные паттерны и структура проекта |
| `naming` | имена новых сущностей |
| `comments` | докблоки новых сущностей |
| `critique` | прогон решения до показа пользователю |
| `review` | взгляд на диф перед завершением |
| `commit` | формат сообщения и порядок коммит/пуш при завершении задачи (по умолчанию сразу) |
