# Комментарии в is_nsi

Главный принцип: **комментарий — короткое и простое объяснение «что это и зачем»**, понятное разработчику, не знакомому с этим функционалом. Комментарии в проекте пишутся на русском языке — так же, как и весь сопроводительный текст.

## Правила

1. **Коротко.** Одна–две строки на свойство или метод. Не пересказывай код: если комментарий читается как «присваивает значение флагу» — он не нужен.
2. **Смысл, а не пересказ.** Пиши то, чего из кода и имени не видно: зачем это нужно, какой контракт у метода, откуда приходят данные.
   - хорошо: `/** Сохранение: отдаёт новое значение родителю, ничего не сохраняет сам */`;
   - плохо (автогенерация-пустышка): `/** Filter of project plan component */`, `/** @returns default cond count */`.
3. **Простые слова.** Те же требования, что в скилле `naming`: частотные слова, никаких «обогащение», «диспетчеризация», «унифицированный». Технические термины уместны, если без них не сказать (например «сигнал», «токен»).
4. **Подробно — только для сложных мест.** Если алгоритм ветвистый (условия по типам страниц, ролям, статусам) — можно расписать шаги, но по делу, без воды. Пример — комментарии в `applyEnterpriseScope` (`pages/plans/components/plan-list/classes/base-table.ts`): каждый комментарий объясняет, чей это сценарий и что исключается.
5. **Комментарий не должен врать.** Изменил поведение — обнови комментарий в том же шаге; устаревший комментарий хуже его отсутствия.
6. **Мусор не оставляем:** закомментированный код, «временное решение» без тикета, «правки по фидбеку» — удалять, а не перевозить за собой.
7. **JSDoc-теги — по необходимости, не пустышками.** `@param`/`@returns` — только когда сигнатура неочевидна сама по себе (флаги-параметры, единицы измерения, допустим `null`) и докблок всё равно пишется; не генерировать их на каждое поле. `@deprecated` — всегда с указанием замены: `/** @deprecated использовать planDocument вместо этого */`.
8. **TODO — только с номером задачи:** `// TODO #7223: добавить проверку прав`. TODO без тикета — это то же «временное решение», удалять.
9. **Язык — русский всегда,** и в англоязычном легаси-файле тоже: новые комментарии русские, существующие английские не переводить без нужды (минимальный диф важнее единообразия).
10. **Шаблоны — те же правила:** `<!-- ... -->` для веток, чей смысл неочевиден (`@if` по статусу/режиму — чей это сценарий); закомментированную разметку — удалять.

## Что документировать

- Класс/компонент — одна строка, что это и где живёт: `/** Общий список планов закупок */`.
- Публичные свойства и методы классов — короткий докблок `/** ... */`, если имя не говорит само за себя.
- Приватные детали с неочевидным смыслом — тоже коротко; очевидное (`isLoading`, `count`) можно не комментировать вовсе.
- Не документируй «на всякий случай» — комментарий без смысла это шум.
