# Коммиты в is_nsi

## Когда коммитить

- По умолчанию — сразу после завершения задачи и self-review: коммит + push, отдельная просьба не нужна.
- Не коммить, если пользователь явно отложил («не коммить», «не пушить», «сначала посмотрю») или попросил
  только показать/сформировать сообщение.
- В `dev`/`master` напрямую не коммить без явной просьбы пользователя.

## Файл gitrules/RULES.md — не этот формат

В репозитории лежит `src/client/ias/src/app/gitrules/RULES.md` — воркфлоу для агентов Cursor
(план → `gitrules/commits.json` → `apply-commits.ps1`, сообщения `#NNNN ...` без тегов, автор коммитов — скрипт).
Это договорённость других разработчиков, а не альтернативный формат этого скила:

- По умолчанию коммить по этому скилу: теги `[add]/[edit]/[refactor]/[gen]`, номер задачи только из ветки.
- Воркфлоу gitrules применять только при явной просьбе пользователя («через gitrules», «по RULES.md»,
  «запусти apply-commits.ps1»).
- Фразы вида «сделай 3 коммита, префикс #6812» без упоминания gitrules — обычный формат этого скила,
  а не переключение на RULES.md.
- Каталог `gitrules/` в каком бы месте репозитория ни появился — не код приложения: при поиске по коду
  его игнорировать, служебные файлы (`commits.json`, `author.json`) в коммиты не включать.

## Формат сообщения

```
[#<номер задачи> ]<[тег]> <текст коммита>
```

Номер задачи пишется только если он есть в имени ветки; тег обязателен всегда. Примеры:

```
#7223 [add] Добавлены 6 и 9 месяцы в блок-станции
[edit] Рефакторинг AddPurchasesComponent
[edit] BE - number опциональный
[gen] swagger
```

## Шаг 1. Номер задачи из ветки

Определи текущую ветку: `git branch --show-current`.

Имена веток с задачей начинаются с номера в форматах `#NNNN-текст`, `#NNNN_текст` или просто `#NNNN`
(реальные примеры: `#7223-Блок-станции-колонки-6-и-9-мес`, `#7060_протяжка_значений`, `#7214`).

- Если ветка начинается с `#NNNN` — пиши этот номер в начале сообщения: `#7223 [edit] ...`.
- Если номера нет в начале ветки (`Планы_закупок_перевести_с_qb_на_rest`, `Metrology-refactoring`, `dev`,
  `рефактор`) — начинай сразу с тега. Числа в середине имени ветки номером задачи не считаются.
- Не выдумывай номер по смыслу изменений — только из ветки.

## Шаг 2. Тег

| Тег          | Когда                                                                       | Примеры из истории                                |
| ------------ | --------------------------------------------------------------------------- | ------------------------------------------------- |
| `[add]`      | Новая функциональность, новые файлы/компоненты/сервисы/эндпоинты            | `[add] Вынесено редактирование строки`            |
| `[edit]`     | Правки существующего кода: доработки, багфиксы, изменение поведения         | `[edit] Исправлена модалка выбора элементов`      |
| `[refactor]` | Рефакторинг без изменения поведения: переименования, переносы, извлечение   | `[refactor] Вынос фильтров в сервис`              |
| `[gen]`      | Сгенерированный код: swagger, gql-кодеген (`gql-build*`)                    | `[gen] swagger`                                   |

- Если коммит смешанный (например, фича + перегенерация swagger) — предпочтительно разбить на два
  коммита с разными тегами. Если пользователь против разбивки — выбирай тег по основной сути коммита.
- Формально новая функциональность, «вынесенная» из существующего кода (новый сервис/компонент без
  изменения поведения) — это `[add]`, как в истории (`[add] Вынесено редактирование строки`);
  если при переносе поведение менялось — `[edit]`.

## Шаг 3. Текст коммита

- По-русски, ёмко, одна строка. Конкретика: что именно сделано и с чем.
- Стиль: краткое причастие / прошедшее время («Добавлены», «Исправлена», «Вынесено», «Удалены»,
  «Перенесён») либо отглагольное существительное («Рефакторинг», «Перенос», «Оптимизация»).
- Без точки в конце, без «исправление мелких багов», без слова «правки» без объекта.
- Называй затронутую сущность, если она одна-две: «Рефакторинг AddPurchasesComponent».
- Уточнение фронта/бэка — префиксом внутри текста: `[edit] BE - number опциональный`.
- По умолчанию сообщение — одна строка. Подробный body (после пустой строки) — только по явной просьбе пользователя или в stage-N рефакторинге: там в body перечисляются детали этапа.
- Не упоминай ИИ и инструменты генерации в тексте.

### Исключение: поэтапный рефакторинг

Если пользователь просит продолжить большой поэтапный рефакторинг, который уже идёт на ветке
(в истории: `ias: refactoring quarterly-plan (stage N): ...`), продолжай в этом же формате:
`ias: refactoring <объект> (stage N, <часть>): подробное описание изменений`. Он используется
вместо короткого формата и включает детали, потому что этапы потом читаются как единая история.

## Процесс коммита

1. `git status` и `git diff` (для незастейдженного) / `git diff --staged` (для застейдженного) —
   пойми суть изменений перед формулировкой. Не коммитить то, что не смотрел.
2. Ничего не стейджить вслепую (`git add -A` запрещён): добавляй конкретные файлы
   (`git add <пути>`), убедись, что артефакты (debug.log, бэкапы, локальные конфиги) не попадают.
3. Если в изменениях несколько логически несвязанных правок — предложи разбить на несколько
   коммитов, каждый со своим тегом.
4. Сообщение передавать через heredoc:

   ```bash
   git commit -m "$(cat <<'EOF'
   #7223 [edit] Исправлена протяжка значений в блок-станциях
   EOF
   )"
   ```

   В PowerShell (OpenCode на Windows) heredoc недоступен: запиши сообщение во временный файл
   в UTF-8 без BOM и выполни `git commit -F <файл>`, затем удали файл.

5. Коммитить только в текущую ветку. В `dev`/`master` напрямую не коммитить — только по явной
   просьбе пользователя.
6. Если пользователь просит только «сформировать сообщение» — покажи сообщение, не выполняя ни
   commit, ни push.
7. После каждого коммита сразу делай `git push` в текущую ветку. Если изменения разбиты на группу
   коммитов — коммить и пушь по одному: коммит → push → следующий коммит → push. Не накапливай
   несколько коммитов ради одного общего пуша в конце: каждый коммит уходит на сервер сразу.
   Исключение — пользователь явно отложил пуш («не пушить», «сначала посмотрю», «потом запушим»):
   тогда ждём отдельной команды на пуш.

## Ветки и MR

- Фичевые ветки — от `dev`; имя `#NNNN-описание` или `#NNNN_описание` (кириллица в именах — норма
  проекта), без номера задачи — осмысленное описание по-русски или транслитом.
- Вливание — через GitLab MR в `dev`, не прямым коммитом в `dev`/`master`.
- Чтобы изменение попало в Changelog релиза, MR метится: `changelog` + метка модуля (`IAS`, `BUY`,
  `NSI`, `PROPLAN`, `BALANCE`, `MID`, `REM`, `CP`, `ASOT`) + метка типа (`Added`/`Changed`/`Fixed`/
  `Removed`) + Milestone версии. Полный регламент — в корневом README репозитория.
- Переписывать историю (rebase с push --force, amend запушенного) и разбирать конфликты при мерже —
  только согласовав с пользователем.

## Антипримеры

- `fix` — нет тега, нет конкретики.
- `#7223 [edit] Исправления` — не сказано, что исправлено.
- `[edit] Правки по фидбеку` — допустимо только, если пользователь сам так сформулировал задачу;
  лучше перечислить суть: `[edit] Исправлены замечания по выручке: пересчет итогов`.
- `Update file.ts` — шаблонный текст, не по конвенции.
- `[refactor] Добавлен новый фильтр` — тег не соответствует содержанию (это `[add]`).
