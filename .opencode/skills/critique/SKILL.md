# Критика решения до показа пользователю

Здесь ты — оппозиционер собственного решения. Задача: найти изъяны до того, как их увидит пользователь или ревьюер. Решение готово к показу, только когда каждая атака из чек-листа либо отбита исправлением, либо осознанно принята как ограничение с формулировкой для пользователя.

Критика не заменяет скиллы `dev` (правила написания кода) и `review` (формат ревью чужого/своего diff) — она выполняется раньше них: до показа решения.

## Процесс

1. Сформулируй решение одной фразой: что меняется и что НЕ меняется. Если не получается — решение ещё не продумано, критика бессильна.
2. Пройди чек-лист по разделам. Для каждого пункта вердикт: найден изъян → исправить; не применимо → сумей объяснить, почему (проверить кодом, не памятью).
3. Изъяны, которые нельзя исправить сейчас, вынеси в «известные ограничения» — их покажешь пользователю вместе с решением.
4. Если исправления существенно поменяли решение — повтори проход по затронутым пунктам чек-листа.
5. Ищи изъяны в коде и данных проекта (прочитай реальное место правки и его потребителей), а не в абстракции: «где-то может быть null» — не изъян; `this._doc.document` без проверки на null в computed — изъян.

## Чек-лист атак

### Краевые случаи и данные

- Что будет при: пустом списке, `null`/`undefined` в поле, нулевом/отрицательном значении, очень длинной строке, повторном клике (double-submit)?
- Все ли прежние сценарии живы: поиском по селектору/классу/токену/методу найди всех потребителей изменяемого кода — что увидят они?
- Модалки: закрытие крестиком и ESC (не сломался ли колбэк), повторное открытие (сбросилось ли состояние/черновик), сохранение во время незавершённого запроса.

### Async и состояние

- Гонки: быстрый повторный запрос, медленный ответ после ухода со страницы, порядок прихода ответов — устаревший ответ, пришедший позже, не должен затирать свежие данные.
- Отписки: каждый `subscribe` в компоненте умирает вместе с ним (`takeUntilDestroyed`/`DestroyService`) или заменён на `firstValueFrom`.
- Ошибки запросов: показаны пользователю (`fail()`/NzMessage), `isLoading` снимается в `finally`, UI не уходит в вечный спиннер.
- Перерисовка при OnPush: изменённые данные дадут новое значение входа/сигнала, а не мутацию по ссылке.

### UI-состояния и права

- Для каждого нового элемента рассмотрены: загрузка, пусто, ошибка, режим просмотра (`viewMode`), отсутствие прав, disabled.
- Кнопка, запускающая запрос, блокируется на время его выполнения.
- Тексты понятны пользователю, а не разработчику; даты/числа форматируются проектными способами.

### Архитектура проекта

- Не попала ли логика данных/сохранения в dumb-компонент?
- Сервис состояния не `providedIn: 'root'`, если он принадлежит странице?
- Не дублируется ли существующее: `gpo-lib`, `src/app/components/`, соседние фичи, утилиты (`src/app/utility/`)?
- Размер: dumb-компонент заметно превышает целевой размер из скилла `dev` — что вынести? Метод больше экрана — как разбить?

### Регрессии и контракт

- Изменение общих компонентов/сервисов/токенов проверено по всем местам использования, а не только по задаче.
- Изменение поведения (а не только структуры) помечено как таковое и не спрятано внутри «рефакторинга».
- Не тронут ли сгенерированные файлы (`@swagger/api`, `graphql/types`) — они только регенерируются.

## Формат результата

Пользователю — кратко, без ритуальной переписки с собой:

- суть решения одной фразой;
- найденные и устранённые изъяны (только существенные, 2–5 пунктов: что было → что исправлено);
- оставшиеся ограничения и допущения, если есть, — явным списком.

Если изъянов не нашлось ни по одному пункту — это сигнал смотреть внимательнее, а не похвала решению.
