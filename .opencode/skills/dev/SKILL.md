# Разработка в is_nsi — главный скил

Входная точка для любой задачи во фронтенде. Остальные скиллы подключаются по маршруту из конца файла; детали архитектуры и рефакторинга — в `references/`, читаются по мере необходимости.

Корень клиента: `src/client/ias` (все пути ниже — относительно него).

Работаем только по коду: браузер и dev-сервер агент не запускает и не открывает, страницы в браузере не проверяет. Визуальную проверку сценария, консоль, Network и Sentry предоставляет пользователь.

## Процесс работы

Порядок шагов обязателен; пропускается только то, чего нет в задаче.

1. **Изучи затронутый код до того, как предлагаешь решение.** Прочитай изменяемые файлы целиком, а не только место правки. Найди всех потребителей: поиск по селектору (`app-…`), имени класса, имени токена и имени сервиса. Типичная ошибка в этом проекте — «сломал соседнюю страницу, которая использовала тот же сервис/компонент». Общий порядок «понять → спроектировать → закодить» для нового функционала и правок — в скилле `architecture`.
2. **Набросай решение в целевой архитектуре** (следующий раздел). Если задача нетривиальна — новая страница, изменение поведения, затрагивает больше двух файлов — покажи план пользователю коротким списком шагов.
3. **Прогони решение через скилл `critique` до показа пользователю** — найди и устрани изъяны заранее: состояния загрузки/ошибок, гонки запросов, OnPush, краевые данные, регрессии у соседних потребителей.
4. **Реализуй маленькими обратимыми шагами.** Один шаг = одна логическая правка. После каждого шага — самопроверка (см. ниже).
5. **Self-review через скилл `review` перед завершением** — посмотри весь свой diff как чужой.
6. **После завершения задачи — коммит и пуш сразу**, через скилл `commit`; отдельная просьба не нужна. Не коммить только если пользователь явно отложил («не коммить», «не пушить», «сначала посмотрю») или попросил лишь показать/сформировать сообщение.

## Целевая архитектура: как писать компоненты

Эталон — страница планов закупок: `src/app/projects/buy/pages/centralized-purshases/pages/plans/components/plan-table/`.

- **Dumb-компонент (UI):** standalone + `ChangeDetectionStrategy.OnPush`; данные — только `@Input()`, события — только `@Output()`; локальный UI-state (видимость режимов, черновики полей) — `signal()`. Ничего не знает о сервисах данных и сохранении. Целевой размер — до ~150 строк.
- **Smart-компонент (контейнер):** провайдит state-сервисы в `providers`, читает их в шаблоне, связывает dumb-компоненты с сервисами — передаёт данные во входы, подписывается на выходы.
- **State-сервисы:** логика страницы — в наборе узких `@Injectable()`-сервисов (без `providedIn: 'root'`, провайдятся на странице): state, actions, document, export, versions… Состояние — `signal`, производные — `computed`, запросы — `async` + `firstValueFrom` с `try/catch/finally` и единым обработчиком ошибок `fail()`.
- **Варианты одной страницы** (полугодовой/оптовый план и т.п.) — не флаги и `if`, а injection-токены: контракт-интерфейс + `InjectionToken`, страница-обёртка подставляет реализацию в `providers`.
- **Модалки** — через `NzModalService.create` с `nzContent`-компонентом и данными в `nzData` (основной способ, см. `plan-page-state.service.ts`); простые предупреждения — `.warning`/`.error`. `AutoInjectorService.open()` — та же модалка, но с типизированными inputs/outputs — допустимо. Не путать: `AutoInjectorService.create()` — не модалка, а overlay-компонент на CDK.
- **Шаблоны:** новый control flow `@if/@for/@let`, в `@for` всегда `track`; ng-zorro-antd — единственная UI-библиотека.
- **Инлайн или отдельные файлы:** если шаблон и стили небольшие (примерно до 100 строк каждый), держи их в ts-файле компонента — `template: \`...\`` и `styles: [...]` — не дроби на отдельные `.html`/`.less`; крупные выноси в `templateUrl`/`styleUrl`.
- **Стили:** LESS рядом с компонентом или инлайн; темы — через существующие LESS-переменные, без хардкода цветов.
- **Имена:** файлы kebab-case, суффиксы `.component.ts`/`.service.ts`/`.pipe.ts`/`.directive.ts`, селекторы `app-*`, барели `_index.ts`. Новые компоненты — standalone; новые NgModule не создавать. Слова в именах — простые и конкретные, понятные без хорошего английского: при выборе имени подключай скилл `naming`.
- **Комментарии:** короткие, простые, объясняют смысл, а не пересказывают код; подробно — только для сложных алгоритмов. Правила — в скилле `comments`.
- **Пути:** общие компоненты — `src/app/components/`, общая либа — `gpo-lib` (`src/app/lib/public-api.ts`), REST — только через `@swagger/api`, GraphQL-типы — только сгенерированные.

Перед созданием нового компонента, страницы или state-сервиса прочитай `references/components.md` — там образцы кода из эталонной страницы и типовые ошибки. Перед написанием/изменением GraphQL-запросов — `references/graphql.md` (расположение, именование, кодеген).

## Как рефакторить

Рефакторинг = поведение не меняется, код движется к целевой архитектуре.

1. **Сначала карта, потом движения.** Определи границы: что станет dumb, где будет состояние, какие входы/выходы, кто потребляет. Составь список шагов и работай по нему.
2. **Один шаг = одна сущность = один коммит** (`[refactor]` в формате скилла `commit`): вынесли сервис, перевели компонент на dumb, разбили метод подготовки данных.
3. **Переносить, а не переписывать.** Логика переносится как есть; переименования — отдельным шагом; изменение поведения — уже `[edit]`, а не `[refactor]`, и его лучше согласовать с пользователем.
4. **После каждого шага — самопроверка** (ниже) и взгляд на diff: ничего лишнего въезжать не должно.
5. **Легаси-гиганты** (2000+ строк: `catalog.component.html`, `technical-economic-indicator-table`, `buy.service`, `nsi.service`) не охватывать целиком — откусывать по одному виджету/методу, наружный контракт сохранять.

Пошаговый порядок перевода страницы на dumb/state-архитектуру — в `references/refactoring.md`; читай перед рефакторингом крупной страницы.

## Самопроверка

- Типы (TS-уровень, быстро): `npx tsc --noEmit -p tsconfig.app.json` из `src/client/ias`. Шаблоны этим не проверяются — их проверяет `ng build` или dev-сервер.
- Линт по затронутым файлам: `ng lint` (eslint 9 + @angular-eslint).
- Формат: 4 пробела, 120 колонок, singleQuote, trailingComma all — как в окружающем коде (prettier).
- UI проверяй по коду: шаблон, импорты модулей и директив (частая причина «кнопка без стилей» в standalone-компоненте), стили и их наследование. Браузер не открывай — визуальную проверку делает пользователь.
- Сгенерированное не правится руками. `@swagger/api` — цикл `npm run swagger` (генерация + фикс + сборка; нужен локальный бэкенд на :10600, без него — `npm run swagger:docker`). GraphQL-типы — `npm run gql-build:<модуль>` (`nsi`, `rem`, `buy`, `mid`, `sign`, `cp` — centralized-purshases), вывод в `src/app/graphql/types/`. Свежесть кодогена проверяет `npm run verify:codegen` — это блокирующий этап сборки.

## Маршрутизация скиллов

| Скилл | Когда подключать |
| --- | --- |
| `dev` (этот) | первым — любая задача разработки |
| `architecture` | проектирование нового функционала и изменений существующего до кода: «нужно добавить/поменять», «где разместить», планирование |
| `naming` | выбор имени для нового класса/метода/поля/переменной, переименование, «имя не нравится», «непонятное имя» |
| `comments` | написание и правка комментариев/докблоков свойств, методов, компонентов; «прокомментируй», «слишком длинный/непонятный комментарий» |
| `critique` | перед показом плана/решения пользователю и перед завершением нетривиальной правки |
| `review` | пользователь просит ревью/проверить код или PR; self-review своего diff перед завершением |
| `commit` | завершение задачи — коммит + push по умолчанию (без отдельной просьбы); также формат сообщения и пуш по запросу |
| `testing` | написание тестов/спеков, «покрой тестами», «прогони тесты»; багфикс в вычислительной логике — тест до фикса |
| `debug` | «не работает», «почему показывает не то», разбор ошибок браузера/Sentry, поиск причины бага |
| `performance` | «тормозит», большие таблицы/списки, тяжёлые расчёты и экспорты, оптимизация |
| `security` | innerHTML/санитизация, токены, Sentry-контент, window.open/внешние ссылки, секреты |
| `ui-texts` | формулировки кнопок/модалок/пустых состояний/ошибок, вывод дат и чисел пользователю |

## Антипаттерны

- Запросы и сохранение внутри dumb-компонента.
- `providedIn: 'root'` для состояния конкретной страницы — состояние утечёт между экземплярами.
- Варианты страницы через флаги `isHalfYear`-типа вместо токенов.
- `subscribe` в компоненте без отписки (`takeUntilDestroyed`/`DestroyService`) — либо `firstValueFrom`.
- Мутация `@Input()` (внутреннего объекта/массива): при OnPush перерисовку даёт новое значение входа/сигнала, а не мутация.
- `any`, `as any`, `@ts-ignore` в новом коде.
- Новые npm-зависимости и новые UI-библиотеки — только с согласия пользователя.
