# Порядок рефакторинга страницы

Плейбук перевода легаси-страницы на целевую архитектуру (dumb-компоненты + state-сервисы + токены).
Опирается на историю рефакторинга страницы планов закупок; шаги выполняются последовательно,
каждый — отдельный коммит `[refactor]` (формат — скилл `commit`), после каждого — компилируемость и проверка.

Главные правила: поведение не меняется, наружный контракт (селекторы, маршруты, входы/выходы используемых снаружи компонентов) сохраняется, логика переносится как есть — улучшать можно форму (куда попал код), не содержание (что он делает).

## Шаг 0. Карта до начала движений

1. Прочитай страницу целиком: шаблон, компонент, все сервисы, которых он касается. Составь список того, что страница делает (загрузка, права, таблица, модалки, экспорт, согласование…).
2. Раздели список на будущие слои: что станет state-сервисами (и каким узким сервисам — state/document/actions/export/versions), что станет dumb-компонентами (какие виджеты), какие данные им нужны как входы и какие события как выходы.
3. Найди всех внешних потребителей: кто использует компонент страницы, его селекторы, сервисы, маршруты. Это границы, которые трогать нельзя.
4. Определи варианты страницы (полугодовой/оптовый план и т.п.) — под них готовится контракт `*_API`/`*_CONFIG`, а не флаги.
5. Согласуй порядок шагов с пользователем, если их больше трёх-четырёх.

## Шаг 1. Вынести контракт данных (если есть варианты страницы)

- Опиши интерфейс всего, что страница просит у бэкенда: методы + группы по смыслу (`approval`, `purchases`, `archive`). Возвращаемые типы — модели страницы или `Observable<…>`.
- `export const X_API = new InjectionToken<XApi>('X_API')` в отдельном файле без суффикса (`plan-table-api.ts`).
- Существующие вызовы переведи на `inject(X_API)`; реализацию по умолчанию выдели в класс, страница-обёртка подставляет её через `providers`.
- Проверка: поведение то же, `tsc --noEmit` чист.

## Шаг 2. Разбить «бог-компонент» на state-сервисы

- Переноси по одному сервису за коммит: сначала документ/версии (данные), потом действия, потом экспорт/согласование. Не один «всё-сервис» — набор узких.
- Состояние, которое читает шаблон, переводи на `signal`; производные (доступность кнопок, флаги режимов) — на `computed`.
- Обработку ошибок собери в один метод `fail()` (NzMessage + Sentry) — не размножай try/catch по компоненту.
- Методы подготовки данных (вида `prepareDataFromServer`) разбивай на функции по смыслу: разделение пар сравнения, форматирование, прикладные правила — у каждой функции одна задача и понятное имя.
- Сервисы — `@Injectable()` без `providedIn`, провайдятся в `providers` smart-компонента страницы.
- Убери привязку к конкретным моделям там, где компонент извлекает значение поля напрямую — пусть получает готовое значение через вход/сервис.

## Шаг 3. Вынести dumb-компоненты

- По одному виджету за коммит (комментарий, карточка сведений, тулбар, фильтры…).
- Виджет становится standalone + OnPush: данные — `@Input()`, события — `@Output()`; локальный UI-state — `signal()`. Всю логику запросов/сохранения из виджета перенеси в state-сервис.
- Модалки виджета открываются из сервиса через `NzModalService` (`inject(NzModalService)`, дальше `.create` с `nzContent`-компонентом или `.warning`/`.error`), не через `AutoInjectorService.open()`.
- Вход «режим просмотра» (`viewMode`/`isXViewMode`) вычисляется в сервисе (права + статус + версия) и подаётся готовым — dumb не собирает его из пяти условий.
- Шаблон переводи на `@if/@for/@let`, `@for` — с `track`.

## Шаг 4. Собрать smart-страницу

- Smart-компонент провайдит все сервисы, в шаблоне связывает dumb-компоненты с ними.
- Тонкие обёртки вариантов страницы (`half-year/table/table.component.ts`-стиль) — только `providers`-подстановка API и конфига.
- Барель `_index.ts` для публичного API фичи.

## Шаг 5. Зачистка

- Удали мёртвый код, оставшийся от переносов (старые поля, методы, импорты), отдельным коммитом.
- Прогони `ng lint` по затронутым файлам, `tsc --noEmit -p tsconfig.app.json`.
- Self-review всего diff ветки по шагам — скилл `review`.

## Чек-лист завершённости одного шага

- Поведение страницы то же (включая режимы просмотра/редактирования, ошибки, загрузку).
- Наружный контракт не изменился; изменился — это отдельный согласованный шаг.
- `tsc --noEmit` чист, линт чист, ничего лишнего в diff.
- Коммит `[refactor]` (или `[add]`, если вынесен новый файл без изменения поведения) сделан по скиллу `commit`.

## Когда остановиться и спросить

- Найдено поведение, которое воспроизвести в новой структуре нельзя без изменений — это уже `[edit]`, согласуй.
- Шаг тянет за собой больше 5–7 файлов — предложи разбить.
- Логика зависит от глобальных сервисов (`nsi.service`, `user.service`) так, что приходится менять их самих — не менять их молча, обсудить.
