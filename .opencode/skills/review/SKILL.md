# Ревью кода

Порядок: сначала суть, потом детали. Ревью без понимания замысла — придирки к строкам.

## Процесс

1. Собери контекст: что ревьюим — diff ветки (`git diff dev...HEAD`), последние коммиты, конкретные файлы или PR. Из задачи/коммит-сообщений пойми замысел: что этот код должен делать.
2. Прочитай diff полностью, затем затронутые файлы вокруг правок — не только изменённые строки: ошибка часто в стыке нового и старого.
3. Найди потребителей изменённого (селекторы, классы, токены, публичные методы) — регрессия оценивается по ним, а не по diff.
4. Пройди чек-лист, по каждому замечанию: место (файл:строка), что не так, к чему приведёт, как исправить.
5. Итог — вердикт и список замечаний по приоритетам.

## Чек-лист

### 1. Корректность — блокер-уровень

- Код делает то, что заявлено задачей; краевые случаи (пустые данные, `null`, границы, double-click) учтены.
- Async: отписки или `firstValueFrom`, гонки запросов, обработка ошибок, снятие `isLoading` в `finally`.
- Нет мёртвых изменений: закомментированный код, debug-логи, случайные файлы, лишние правки не по задаче.

### 2. Архитектура — соответствие целевой (скилл `dev`)

- Dumb-компоненты — только `@Input`/`@Output` и UI-state на `signal`; логика запросов и сохранения — в state-сервисах страницы.
- Сервисы состояния страницы — `@Injectable()` в `providers` страницы, не `providedIn: 'root'`.
- Варианты страницы — через `InjectionToken` + `providers` обёртки, не флаги и `if`.
- Новое не дублирует существующее: `gpo-lib`, `src/app/components/`, утилиты, соседние фичи.

### 3. Конвенции проекта

- standalone + `OnPush`; шаблоны на `@if/@for/@let`, `@for` с `track`; только ng-zorro-antd.
- Имена: kebab-case файлы, суффиксы `.component.ts`/`.service.ts`, селекторы `app-*`, барели `_index.ts`.
- Формат: канон — в скилле `dev` (4 пробела, 120 колонок, singleQuote); здесь не дублируется.
- Сгенерированное (`@swagger/api`, `graphql/types`) не правилось руками.

### 4. Производительность — по месту

- Тяжёлые вычисления и фильтрации — в `computed`, не в методах, вызываемых из шаблона на каждый цикл проверки.
- Нет порождения новых массивов/объектов в шаблонных выражениях без нужды.
- Подписки не дублируют друг друга; нет цепочек запросов, которые можно объединить.
- Готовые механизмы (виртуализация gpo-lib, серверный пейджинг, воркеры, `memoDictionary`) — не изобретается ли своё рядом с существующим? Подробности — скилл `performance`.

### 5. Регрессии и безопасность

- Изменения общих компонентов/сервисов проверены по всем местам использования.
- Режимы просмотра и права (`viewMode`, роли, `canXxx()`) не обходятся новыми элементами.
- XSS: `[innerHTML]` с недоверенным контентом, `bypassSecurityTrust*` без обоснования, токены/персональные данные в Sentry, `window.open(_blank)` без noopener — по чек-листу скилла `security`; такое — P1.

## Приоритеты замечаний

- **[P1] блокер** — ошибка или высокий риск регресса; без правки не мержить.
- **[P2] желательно** — отступление от целевой архитектуры/конвенций; исправить в этой же ветке.
- **[P3] nitpick** — стиль, именование, мелочь; на усмотрение автора.

Замечание без места (файл:строка), последствия и предложения исправления — не замечание, а мнение; не писать. Замечания группируй по файлам, не по чек-листу — так их быстрее обрабатывать.

## Итог ревью

Вердикт одним из: **принять** / **принять с правками** (перечислены P2/P3) / **переработать** (есть P1). После вердикта — список замечаний и, для self-review, что исправлено сразу.

## Что НЕ считать замечанием

- Форматирование, где его выравнивает prettier/окружающий код.
- Легаси-код рядом с diff, который правка не трогает (одной строкой «вокруг легаси, вне scope» — можно, разбирать его — нет).
- Личные предпочтения без указания вреда: «я бы вынес» без того, почему это сломается или усложнит жизнь.

## Self-review собственных изменений

Тот же чек-лист, но вход — полный diff своих изменений (`git diff` + `git diff --staged`), и два дополнительных вопроса: «что я мог сломать в местах, которые не смотрел» и «что в diff въехало случайно». После исправления найденного — коммит через скилл `commit`.
