# Тестирование в is_nsi

В проекте карма+jasmine, но философия специфичная: **тестируется вычислительная логика, а не обвязка**. Не гонись за покрытием компонентов и запросов — пиши точные тесты там, где логика действительно живёт.

## Что тестировать

Обязательно:

- **Чистые функции и утилиты** — резолверы, мапперы, сборка условий фильтров, форматирование (примеры в проекте: `projects/proplan/utils/public-code-resolver.spec.ts`, `flatten-settings.spec.ts`).
- **Signal-сторы и state-сервисы без тяжёлых зависимостей** — переходы состояний, иммутабельность, производные `computed` (пример: `constructor-config.store.spec.ts`, `table-config.service.spec.ts`).
- **Багфикс в логике** — сначала тест, воспроизводящий баг (красный), потом фикс (зелёный). Тест остаётся как регрессионный.

Не пишутся (осознанный выбор проекта, не пробел):

- Тесты dumb-компонентов «на перерисовку» и снапшоты шаблонов.
- Тесты, мокающие Apollo/NzMessage/роутер, — слой запросов и показа ошибок проверяется в браузере, а не спеками (`jasmine.createSpyObj` в проекте не используется).
- Тесты сгенерированного кода (`@swagger/api`, `graphql/types`).

## Паттерны (как в реальных спеках проекта)

1. **Чистая функция — без TestBed вообще:**

   ```ts
   const row = (patch: Partial<Row> = {}): Row => ({ code: '1', ...patch }); // фабрика с дефолтами

   it('филиал п.1 под 1.1 получает 1.1.1', () => {
       expect(buildResolvedPublicCodesMap([row({ code: '1' }), row({ code: '1.1' })])).toEqual(...);
   });
   ```

2. **Signal-стор — инстанс напрямую, состояния через `.set()`, проверки ссылок:**

   ```ts
   const store = new ConstructorConfigStore();
   const before = store.config();
   store.updateRowsTemplateField(...);
   expect(store.config()).not.toBe(before);   // новое состояние — новый объект
   expect(store.config()).toBe(before);       // no-op не создаёт новый объект
   ```

3. **Сервис с зависимостями — TestBed только для DI, без моков окружения:**

   ```ts
   beforeEach(() => TestBed.configureTestingModule({ providers: [TableConfigService] }));
   service = TestBed.inject(TableConfigService);
   ```

Дополнительно:

- Спек лежит рядом с файлом: `foo.ts` → `foo.spec.ts` в той же папке.
- Описания `it` — по-русски, по бизнес-кейсам: «филиал п.1 под 1.1 получает 1.1.1, даже если…» — так тест читается как документация правила.
- Фабрики-литералы вместо моков: `minimalConfig()`, `row(patch)` со spread-дефолтами; при нехватке типов — `as unknown as <Тип>` в фабрике, не в тестах.
- Асинхронщина (`fakeAsync`, `tick`, `done`) в проекте не используется — если логика требует асинхронного теста, скорее всего её стоит вынести в синхронную чистую функцию.

## Запуск и проверка

- **Проверка своих спеков без браузера** (основной режим для агента): типы и компиляция — `npx tsc --noEmit -p tsconfig.spec.json` из `src/client/ias`. Для спеков конструктора Proplan есть отдельный лёгкий конфиг: `npm run test:constructor-spec` (это typecheck, НЕ запуск jasmine — полного прогона без сборки проект не предусматривает).
- **Полный прогон** `npm test` (karma) открывает Chrome в watch-режиме и не завершается сам; набор целиком тяжёлый по памяти и содержит ~45 старых CLI-стабов `should create`, которые падают на компонентах с зависимостями. Запускай только по явной просьбе пользователя и предупреждай об этом.
- Свежесть сгенерированных типов для спеков: `npm run verify:codegen`.

## Чего не делать

- Не обновлять и не «чинить» старые CLI-стабы `should create` без просьбы — они вне здоровья набора.
- Не писать тест ради теста: если нечего проверить утверждением о поведении — тест не нужен.
- Не мокать то, что можно инстанцировать: чистая логика тестируется реальными объектами.
